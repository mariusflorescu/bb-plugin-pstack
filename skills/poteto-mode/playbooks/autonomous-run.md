### Autonomous run

**You own the exit condition. Define done, then drive to it without stopping.**

1. State the exit condition as a checkable predicate before the first iteration (tests green, repro fixed, all N PRs merged, pixel-diff zero).
2. Pick the wake mechanism. An event to watch (CI, a merge, a ref advancing, a child thread finishing) gets a background command in this thread that exits on the event, so its exit wakes you. Use `bb thread wait <id>` for a child thread, `scripts/watch-pr/watch-pr` for a PR, and a short poll loop for a ref. Back it with a long time-based heartbeat, an automation that re-prompts this thread on a long interval such as hourly. A cron fires every interval until you delete it, so the fallback outlives each firing. `--in` and `--at` fire once. A targeted run keeps this thread's provider and model, but it runs in the permission mode the automation stores, `auto` or `full` when none is given, so read this thread's mode from its last turn with `bb thread log "$BB_THREAD_ID" --json --all | jq -r '[.[] | select(.type == "client/turn/requested")][-1].data.execution.permissionMode'`. Without `--environment`, BB checks the provider on the BB server's machine instead of this thread's, and it refuses `--environment` together with `--target-thread`. So create the heartbeat paused on this thread's environment with `bb automation create --project "$BB_PROJECT_ID" --name "<run> heartbeat" --disabled --cron '<expression>' --timezone <IANA zone> --environment "$BB_ENVIRONMENT_ID" --provider <provider> --model <model> --permission-mode <this thread's mode> --prompt "<resume prompt>" --json`, with the provider and model from the "You run on" line of the pstack delegation rules. Aim it at this thread with `bb automation update <id> --project "$BB_PROJECT_ID" --target-thread "$BB_THREAD_ID"`, and start it with `bb automation resume <id> --project "$BB_PROJECT_ID"`. When the operator changes this thread's permission mode, match it with `bb automation update <id> --project "$BB_PROJECT_ID" --permission-mode <mode>`. No event gets a fixed-interval heartbeat, the same commands with the cron sized to when the result is worth re-checking. Record the `id` the create prints and delete it with `bb automation delete <id> --project "$BB_PROJECT_ID" --yes` when the run stops.
3. Each iteration makes the smallest change the evidence justifies, verifies it against the predicate, commits if it advanced, discards changes that didn't help. Belt-and-suspenders that "might help" gets reverted, not left to ride.
   Sequence the work via the **sequence-verifiable-units** principle skill, verifying each unit before the next instead of batching checks at the end.
4. Mid-run discoveries are yours. Address broken skills, related bugs, flaky verifiers, review noise, tooling failures, orphaned follow-ups, and fixable drift yourself via poteto-mode. Put out-of-band fixes in their own PR. Do not park reversible work for the human or stop to ask the user. Surface only irreversible actions, genuine product or preference calls no experiment can settle, or a real dead end. Keep the predicate as the main drive, and return to it after each side fix.
5. Checkpoint every iteration via the **show-me-your-work** skill, a row for what changed and whether the predicate moved.
6. Stop when the predicate is met. A plateau is not a stop, so keep going and pivot your approach to push past it. Surface a genuine dead end rather than spinning, and never relax the predicate to declare victory.

**Reply:** the exit condition, iterations run, what landed, what was discarded, final predicate state.
