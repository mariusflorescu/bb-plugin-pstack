### Pause safely

**You own a clean stop. Leave a checkpoint a cold-start agent can resume from.** This is explicit only. On "keep going", "going to bed, keep going", or "don't stop", do not pause.

1. Stop at a safe boundary. Finish the current atomic step or back out of it. Start nothing new, and cancel any nested subagents with `scripts/pause-tree.sh "$BB_THREAD_ID"` from this skill's directory. It pauses every automation that would re-prompt this thread or a descendant, in each project a thread of the tree lives in, discards the queued messages this program created on this thread and its descendants (tells sent from this tree, due notices of automations this tree created), then stops every descendant thread at any depth, hidden ones included, until one pass finds them all settled. A descendant is any thread BB's archive of this thread reaches: a child, a lifecycle dependent or a hidden fork, at any depth. A fork reuses its source's environment by default and reports to no one, so nothing else notices it running. A machine can still run a turn for a thread BB lists as idle or error, and only an explicit stop interrupts it, so the script stops each descendant at least once whatever its listed status, and counts it settled only after that stop succeeded and a later pass lists it idle or error. A stop leaves a thread's terminals running, so a CLI a stopped descendant started would keep writing through the pause. The script closes every live terminal scoped to a descendant it stopped with `bb terminal close <id> --if-clean --json`, and counts that descendant settled only once a later `bb terminal list --thread <id>` shows none. `--if-clean` leaves open a terminal that anyone sent input to, typed in the UI or sent with `bb terminal send`, since someone may be working in it. The script never force-closes one: it names it with the time of its first input and exits non-zero. It never stops this thread and never touches its terminals. `bb thread stop` leaves a queue intact, so any other queued message (the user's, a retry, another program's) would restart its thread later. The script leaves those queued and never stops their threads. Never delete one yourself. Before each delete, it saves the message to `$BB_THREAD_STORAGE/pause-tree-<thread-id>.jsonl` as one JSON row per message `id` with the target `threadId`, the `senderThreadId` and the `content`, then reads it back. Before each close, it saves the terminal to the same file as a row with `"kind": "terminal"`, the owning `threadId`, the `title` (the command unless one was given) and the `initialCwd`. Every row also carries its `route`: the threads the script walked from this thread down to the row's `threadId`, each with the `link` it hangs by from the one before (`child`, `dependent` for a lifecycle dependent, `fork` for a hidden fork). Each stop prints the same route, as `stopped <id> via <route>`. If a save fails, it stops there with `error: cannot save`, discards and closes nothing more and leaves the tree unsettled, so fix the storage and rerun it. Every run of the script adds to that one file. Right after the last run for this pause, move it to `$BB_THREAD_STORAGE/pause-<time>.jsonl`, where `<time>` comes from `date -u +%Y%m%dT%H%M%SZ`. When the runs discarded and closed nothing, the file does not exist, so create `pause-<time>.jsonl` empty instead. An empty file means this pause has nothing to replay. A later pause then starts a fresh file, and each resume replays only its own pause. A non-zero exit names the threads still running, every message left queued on them, and every terminal left open. A message on this thread from outside the program stays queued too and is named, but does not fail the run, since it wakes only this thread. Do not checkpoint while a named thread is running, and name each message left queued, this thread's included, to the operator. Name each terminal left open to the operator too, and wait for their decision. Close one only on their say-so, with `bb terminal close <id>`, then rerun the script. If they keep it, it runs through the pause, so name it in the resume note.
2. Take no irreversible action to pause. No PR and no push unless you already had one out.
3. Make the work durable. Commit uncommitted edits as one clear `wip:` commit on the current branch so nothing is lost. If the tree is broken, say so in the commit body in one line.
4. Write the resume note off-context. Capture intent, what you were doing, progress and what's verified, current state, next steps, key files, gotchas, the automations the script paused with the project it prints for each (`paused automation <id> in <project>`), the threads it stopped with the route it prints for each (`stopped <id> via <route>`), the absolute path of this pause's `pause-<time>.jsonl`, and that the resume follows step 5 before anything else. For the compaction trigger write it to a file like `$BB_THREAD_STORAGE/<slug>-resume.md`. If a show-me-your-work trail exists, point at it instead of duplicating it.
5. On resume, recover before you replay. A replayed message or a resumed automation starts a turn on the thread it reaches, and a tell to a thread the script stopped restarts it mid-step. So recover each direct descendant of the paused thread (a child, lifecycle dependent or hidden fork of it) before anything wakes it or a thread under it. Walk the graph the script walked, as it recorded it: a thread is under the first hop of its route. That covers the first hop of the route of every row of `pause-<time>.jsonl`, of every paused automation's target (`targetThreadId` or `execution.targetThreadId` in `bb automation show <id> --project <project> --json`, routed by its `stopped` line), and of every other stopped thread you mean to wake. A row aimed at the paused thread has an empty route. Each resume attempt takes one attempt id, `pause-<time>-r<now>`, where `<now>` comes from `date -u +%Y%m%dT%H%M%SZ` when the attempt starts, so no two attempts share one. Send each of those descendants its recovery message with `bb thread tell <thread-id> --message-file <path> --json`. The message carries the attempt id, says its last turn was cut mid-step and the threads under it were stopped, and names each of them with its route. The descendant re-reads its branch, worktree and those threads, replies `RECOVERED <attempt id> <head SHA>` with what it found, and writes nothing until your go. A `queued` delivery waits on that descendant's open interaction. Do not resend it. Name the interaction to the operator. Collect each reply in the background by repeating `bb thread wait <thread-id>` then `bb thread output <thread-id>`, a few seconds apart, until the output starts with `RECOVERED <attempt id> `. Only that output is the acknowledgement. `bb thread wait` returns at once on a thread still idle before the request starts, and `bb thread output` is the thread's latest reply, whichever request produced it, so an output without this attempt id is an earlier recovery's or another turn's. A queued recovery stays pending until its row has run and the reply carries the id. Only after a descendant's acknowledgement, send it its go with `bb thread tell`. The go quotes each row whose route starts at that descendant, with the row's `threadId`, `senderThreadId` and `route`. The descendant acts on each row that is still current, and resends or replaces each subagent's work. A `terminal` row is a terminal the script closed: the descendant restarts it with `bb terminal create --thread <threadId> --title <title> --command <command>` only if its work still needs it. Read the rows aimed at the paused thread yourself. As soon as the tell carrying a row succeeds, or you have read the row, append its `id` to `pause-<time>.sent` beside the `.jsonl`. Skip every `id` already there, so a retried resume never resends one. Resume each paused automation with `bb automation resume <id> --project <project>` only after every descendant you woke has acknowledged and taken its go. Resume by trigger, read from `bb automation show <id> --project <project> --json`: a recurring (`cron`) trigger, or a one-shot whose run time is still ahead, resumes directly. BB refuses to resume a one-shot whose run time passed during the pause, so if its work is still needed, give it a new time with `bb automation update <id> --project <project> --in <duration>` first, and if it already ran or its work is done, leave it paused and log that.

**Reply:** where you are in the loop, what's on disk versus still in your head (paths, no diff dumps), the commits you made and whether the tree is clean, and the first action on resume. This is a pause, not a final report.
