### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, arm a `/goal` with the full program objective if the root thread's provider offers the `goal` action in `bb provider list --environment "$BB_ENVIRONMENT_ID" --json` (Codex does). The goal continues across turns until the queue is done. When the provider has no `goal` action, log the full program objective as a row of your decision trail per the **show-me-your-work** skill, and step 6's tick automation carries the program across turns.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** The forge is GitHub, through GitHub CLI (`gh`), for every PR operation. Never require Graphite (`gt`). One owner per PR, a child thread on the code model for that PR's playbook in its own worktree (`bb thread spawn --parent-self --new-environment worktree`), owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical review-bot triage per `../references/bugbot-triage.md`, a slop-strip (a de-slop or simplify skill if the session lists one, otherwise a review pass by your refactoring model), `/no-comments` (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and `/no-comments`, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **swarm** skill and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with the project's own verification skill, BB's browser (`bb guide browser`) for a web UI, a BB terminal (`bb guide terminals`) for a CLI or TUI, or a named driver where none fits). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner merges and takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. If trunk moves again before the merge, the patch-id rule in `playbooks/shipping.md` governs re-verification. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR with `gh pr merge <pr> --squash` and picks up its next self-contained item from the queue. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners roughly every 30 minutes. Arm the cadence once with `bb automation create --project <project-id> --name "<program> audit tick" --cron "*/30 * * * *" --timezone <tz> --target-thread <root-thread-id> --provider <provider> --model <model> --prompt "Audit tick. Run poteto-mode playbooks/autopilot-full.md step 6."`, a recurring automation that re-prompts this root thread on its own provider and model. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk with `scripts/read-from-trunk.sh skills/poteto-mode/playbooks/autopilot-full.md` and log the trunk revision it prints in your decision trail, then re-read the program objective from step 1, the armed `/goal` or its decision-trail row. If the script fails, log its error, tell the operator once, and audit against the loaded `playbooks/autopilot-full.md` until it reads again. Audit the operation against both. Fix drift during that tick. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. `bb thread stop` does not cascade, so stand down the lane's whole tree with `scripts/pause-tree.sh <id>`. It pauses every automation aimed at the lane or a descendant, discards the queued wake-ups that tree created, and stops every descendant at any depth until one pass finds them all settled. The lane's own queue and a stopped child's report can still wake the lane, so settle it next: clear the program's rows from `bb thread queue list <id> --json`, then run `bb thread stop <id>`. To clear the program's rows on a thread, cancel a retry that `bb provider-retry status <thread-id>` lists with `bb provider-retry cancel <thread-id>` (a disabled plugin lists none). Delete each report or tell from a thread of this program, and each due notice of an automation the script paused, with `bb thread queue delete <thread-id> <message-id>`. The lane is settled when `bb thread show <id> --json` gives a `.thread.status` other than `pending`, `starting`, `active`, or `stopping`, and its queue is empty. The replacement takes the lane's branch, PR, and merge only after the script exits 0 and the lane is settled. Until then, the replacement builds on a fresh branch in its own worktree. It does not push the lane's branch or open, edit, or merge its PR. A non-zero exit names each thread still running and each message left queued. Clear the program's rows among them and rerun the script. Name the rest to the operator, and rerun once the operator settles them. Log the stand-down in your decision trail with the automations the script paused and the discarded-messages file it names, and put both in the replacement's brief. Each tick also runs the lane stuck test over the program's child threads (`bb thread list --parent-thread <id> --include-hidden --json` for the root and for each owner) and over every ID in every owner's `children.tsv`, read with `bb thread show <id> --json`, since a list pages a bounded window. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick automation only when no delegated work is left in any `children.tsv` or child list, even after the last merge, with `bb automation delete <automation-id> --project <project-id> --yes`.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. A `bb thread tell` is not that order: an owner blocked on an open question or approval cannot take a prompt, so the tell only queues. Stop the program instead with `scripts/pause-tree.sh "$BB_THREAD_ID"` from the root, as in `playbooks/pause-safely.md` step 1. It pauses the tick automation, so no tick reads a held owner as stuck, and every other automation aimed at the root or an owner. It discards the program's queued wake-ups and stops every owner and subagent at any depth, until one pass finds them all settled. A stop ends the live turn and keeps the owner's history, worktree, and brief. Exit 0 confirms the hold. A non-zero exit names each thread still running and each message left queued, which would restart its owner later. Tell the operator at once which owners the hold does not yet cover, name each message, and rerun the script once the operator settles them. Record the hold as a row of your decision trail: each owner with its status from `bb thread show <owner-thread-id> --json` and its last head SHA, the automations the script paused, and the discarded-messages file it names. Owners hold their briefs until the operator releases them. On release, resume each paused automation with `bb automation resume <automation-id> --project <project-id>`, re-send the discarded messages, and send each owner the release with `bb thread tell <owner-thread-id> --message-file <path> --json`. The release says its last turn was cut mid-step and its subagents were stopped, so it re-reads its branch, PR, and `children.tsv` before its next write. A `queued` delivery waits on that owner's open interaction. Do not resend it.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
