### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** The forge is GitHub, through GitHub CLI (`gh`), for every PR operation. Never require Graphite (`gt`). One owner per PR, a child thread on the code model for that PR's playbook in its own worktree (`bb thread spawn --parent-self --new-environment worktree`), owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical review-bot triage per `../references/bugbot-triage.md`, a slop-strip (the **deslop** skill (`/deslop`)), `/no-comments` (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and `/no-comments`, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **swarm** skill and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with the project's own verification skill, BB's browser (`bb guide browser`) for a web UI, a BB terminal (`bb guide terminals`) for a CLI or TUI, or a named driver where none fits). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `playbooks/shipping.md`, a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR with `gh pr merge <pr> --squash` and returns. A fresh owner picks up the next self-contained item from the queue, per poteto-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, arm the cadence once, as a recurring automation that re-prompts this root thread on its own provider, model, machine, and permission mode. An automation sends each tick in the permission mode it stores, `auto` or `full` when none is given, so read the root's mode from its last turn with `bb thread log "$BB_THREAD_ID" --json --all | jq -r '[.[] | select(.type == "client/turn/requested")][-1].data.execution.permissionMode'`. Without `--environment`, BB checks the provider on the BB server's machine instead of the root's, and it refuses `--environment` together with `--target-thread`. So create the automation paused on the root's environment with `bb automation create --project "$BB_PROJECT_ID" --name "<program> audit tick" --disabled --cron "0 * * * *" --timezone <tz> --environment "$BB_ENVIRONMENT_ID" --provider <provider> --model <model> --permission-mode <root-mode> --prompt "Audit tick. Run poteto-mode playbooks/autopilot-full.md step 6." --json`, aim it at the root with `bb automation update <automation-id> --project "$BB_PROJECT_ID" --target-thread "$BB_THREAD_ID"`, and start it with `bb automation resume <automation-id> --project "$BB_PROJECT_ID"`. When the operator changes the root's permission mode, match it with `bb automation update <automation-id> --project "$BB_PROJECT_ID" --permission-mode <mode>`. Never leave the cadence to memory or lossy completion notifications. At each tick, first look in your decision trail for a step 7 hold with no release logged after it. While one stands, the tick only logs itself there and ends. It does not probe, stand down, replace, or tell any owner until the operator's explicit release. Otherwise, re-read this playbook from trunk with `scripts/read-from-trunk.sh skills/poteto-mode/playbooks/autopilot-full.md` and log the trunk revision it prints in your decision trail. If the script fails, log its error, tell the operator once, and audit against the loaded `playbooks/autopilot-full.md` until it reads again. Audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. `bb thread stop` does not cascade, and a lane still running can spawn or restart a child after its tree is stopped, so stand down the lane and its whole tree together with `scripts/pause-tree.sh --stop-target <id>`. Each pass stops the lane first, pauses every automation aimed at the lane or a descendant, discards the queued wake-ups that tree created, stops every descendant at any depth, and closes the terminals of each thread it stopped with `--if-clean`, saving each message and terminal to the file it names before it discards or closes it. It exits 0 only when one pass finds the lane and every descendant settled together. A non-zero exit names each thread still running, each message left queued, and each terminal left open because someone typed in it. The script counts only the lane's tree as the program, so among those messages a tell you or another owner sent, the due notice of an automation it paused, and a retry of a turn in that tree (`payload.kind` is `retry` in `bb thread queue list <thread-id> --json`) are the program's: append each row whole to that file and read it back, since a stall never drops the work, delete it with `bb thread queue delete <thread-id> <message-id>`, and rerun the script. Name the rest to the operator, never force-close a terminal someone typed in, and rerun once the operator settles them. The replacement takes the lane's branch, PR, and merge only after the script exits 0. Until then, the replacement builds on a fresh branch in its own worktree. It does not push the lane's branch or open, edit, or merge its PR. Log the stand-down in your decision trail with the automations the script paused and the file it names, and put both in the replacement's brief. The replacement reconciles every message in that file with its assignment and restarts each saved terminal whose work is still needed. Each rerun appends to the file, so the handover tell names it again. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose thread cannot start a turn. Each tick also runs the lane stuck test over the program's child threads (`bb thread list --parent-thread <id> --include-hidden --json` for the root and for each owner) and over every ID in every owner's `children.tsv`, read with `bb thread show <id> --json`, since a list pages a bounded window. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick automation only when no delegated work is left in any `children.tsv` or child list, even after the last merge, with `bb automation delete <automation-id> --project <project-id> --yes`.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. A `bb thread tell` is not that order: an owner blocked on an open question or approval cannot take a prompt, so the tell only queues. Log the hold as a row of your decision trail first, since every tick checks for it before anything else (step 6). Then stop the program with `scripts/pause-tree.sh "$BB_THREAD_ID"` from the root, as in `playbooks/pause-safely.md` step 1. It pauses the tick automation and every other automation aimed at the root or an owner. It discards the program's queued wake-ups on the root and on every owner and subagent, the tick's due notices included, and stops every owner and subagent at any depth, until one pass finds them all settled. A stop ends the live turn and keeps the owner's history, worktree, and brief. A pause does not recall a tick BB already began to deliver, so one can still reach the root after the script. The hold row keeps it from reading a held owner as stuck. Exit 0 confirms the hold. A non-zero exit names each thread still running, each message left queued, which would restart its thread later, and each terminal left open because someone typed in it, which only the operator may close. Tell the operator at once which owners the hold does not yet cover, name each message, and rerun the script once the operator settles them. Every run appends to the one discarded-messages file it names, so right after it exits 0, move that file to `$BB_THREAD_STORAGE/hold-<n>.jsonl`, `<n>` being this hold's number in your trail. When the run discarded nothing the file does not exist: create `hold-<n>.jsonl` empty instead. An empty file means this hold has nothing to replay. A later hold then starts a fresh file, and each release replays only its own hold. Complete the hold row: each owner with its status from `bb thread show <owner-thread-id> --json` and its last head SHA, the automations the script paused with the project it prints for each, and the path of `hold-<n>.jsonl`. Owners hold their briefs until the operator releases them. A replayed message or a resumed automation starts a turn on the thread it reaches, so the release recovers each owner before anything else can wake it. On release, log the release in your decision trail. The release takes one attempt id, `hold-<n>-r<now>`, where `<now>` comes from `date -u +%Y%m%dT%H%M%SZ` when the release starts, so no two attempts share one. Send each owner its recovery message with `bb thread tell <owner-thread-id> --message-file <path> --json`. The message carries the attempt id and says the owner's last turn was cut mid-step and its subagents were stopped, so the owner re-reads its branch, PR, and `children.tsv`, replies `RECOVERED <attempt id> <head SHA>` with what it found, and writes nothing until the root's go. A `queued` delivery waits on that owner's open interaction. Do not resend it. Name the interaction to the operator. Collect each reply in the background by repeating `bb thread wait <owner-thread-id>` then `bb thread output <owner-thread-id>`, a few seconds apart, until the output starts with `RECOVERED <attempt id> `, and log it with its head SHA. Only that output is the acknowledgement. `bb thread wait` returns at once on a thread still idle before the request starts, and `bb thread output` is the thread's latest reply, whichever request produced it, so an output without this attempt id is an earlier release's or another turn's. A queued recovery stays pending until its row has run and the reply carries the id. Only after an owner's acknowledgement, send it its go with `bb thread tell`. The go quotes each row of `hold-<n>.jsonl` aimed at that owner or at a thread under it, with the row's `threadId`, `senderThreadId` and `route`. A row's owner is the first hop of its `route`, the chain of child, lifecycle-dependent and hidden-fork links `pause-tree.sh` recorded from the root, not a climb up `parentThreadId` (a dependent or a fork has none). A first hop that is not an owner, such as a hidden fork or lifecycle dependent of the root, gets the same recovery and acknowledgement before any row routed through it is replayed. The owner acts on each row that is still current, and resends or replaces each subagent's work as its `children.tsv` decides. Read the rest, the rows aimed at the root or its own lanes, yourself. As soon as the tell carrying a row succeeds, or you have read it, append the row's `id` to `$BB_THREAD_STORAGE/hold-<n>.sent`. Skip every `id` already there, so a retried release never resends one. Resume each paused automation with `bb automation resume <automation-id> --project <project>` only after every owner has acknowledged and taken its go. Resume by trigger, read from `bb automation show <automation-id> --project <project> --json`: a recurring (`cron`) trigger, or a one-shot whose run time is still ahead, resumes directly. BB refuses to resume a one-shot whose run time passed during the pause, so if its work is still needed, give it a new time with `bb automation update <automation-id> --project <project> --in <duration>` first, and if it already ran or its work is done, leave it paused and log that.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
